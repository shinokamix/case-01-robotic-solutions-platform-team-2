# План реализации

## 1. Контракт и хранение учетных записей

- [x] 1.1 [backend] Описать в OpenAPI маршруты регистрации, входа и получения текущей сессии под базовым путем `/api` с единым форматом ошибок и ролей
  - Проверка: OpenAPI задает сервер `/api` и содержит ресурсные пути `POST /auth/register`, `POST /auth/login` и `GET /auth/me`; итоговые адреса имеют вид `/api/auth/*`; `RegisterRequest` требует `email`, `firstName`, `lastName` и `password`; ответы содержат `id`, `email`, `firstName`, `lastName` и `role`; схема проходит проверку
  - Зависит от: нет

- [x] 1.2 [backend] Добавить миграции PostgreSQL для учетных записей и серверных сессий с уникальным email, именем, фамилией, ролью и сроками истечения
  - Проверка: миграции применяются на чистой базе, повторный email отклоняется ограничением, имя и фамилия сохраняются, состояние сессии хранится без пароля
  - Зависит от: 1.1

- [x] 1.3 [backend] Реализовать каноникализацию email, проверку длины пароля от 12 до 128 символов и хеширование Argon2id с зафиксированными параметрами
  - Проверка: пробелы по краям удаляются, local-part и IDNA-домен каноникализируются в нижний регистр, проверяются точки и допустимые символы, адрес длиннее 254 символов или содержащий внутренние пробелы отклоняется с кодом `invalid_email`, символ `+` сохраняется, одинаковые канонические email считаются одним значением, пароль короче 12 или длиннее 128 символов отклоняется с кодом `invalid_password`, хеш содержит алгоритм и параметры, открытый пароль не попадает в базу и ответы API
  - Зависит от: 1.2

## 2. Регистрация и вход

- [x] 2.1 [backend] Реализовать регистрацию с именем и фамилией, автоматической ролью `user`, серверной сессией и ограничением частоты запросов
  - Проверка: уникальная регистрация сохраняет имя и фамилию, создает пользователя и сессию, пустые или слишком длинные имя и фамилия получают ошибки `invalid_first_name` или `invalid_last_name`, повторный email получает ошибку без создания второй записи, роль из запроса не назначается
  - Зависит от: 1.3

- [x] 2.2 [backend] Реализовать вход по email и паролю с общей ошибкой для неизвестного email и неверного пароля
  - Проверка: корректные учетные данные создают сессию и возвращают роль, неверные учетные данные не создают сессию и не раскрывают существование email
  - Зависит от: 1.3

- [x] 2.3 [backend] Настроить серверную сессию со скользящим таймаутом бездействия 14 дней и абсолютным таймаутом 30 дней
  - Проверка: активная сессия продлевается в пределах 14 дней бездействия, после 14 дней без запросов или 30 дней с момента создания защищенный запрос требует новый вход
  - Зависит от: 2.1, 2.2

- [x] 2.4 [backend] Настроить атрибуты сессионной cookie `HttpOnly`, `Secure` в сетевом окружении и `SameSite=Lax` или более строгий режим
  - Проверка: заголовок cookie содержит требуемые атрибуты, пароль и идентификатор пользователя не хранятся в cookie
  - Зависит от: 2.3

- [x] 2.5 [backend] Защитить изменяющие запросы регистрации и входа от CSRF и ограничить повторные попытки входа
  - Проверка: запрос без требуемой CSRF-защиты отклоняется, серия неудачных попыток входа получает ограничение частоты
  - Зависит от: 2.1, 2.2

- [x] 2.6 [backend] Исправить ограничение частоты запросов для работы за доверенным reverse proxy
  - Проверка: API принимает forwarded IP только от настроенных доверенных прокси, входы разных email за одним прокси не блокируют друг друга общим счетчиком, прямой клиент не может подменить IP заголовком, истекшие счетчики удаляются, а правила подключены к операциям авторизации без сравнений строк URL
  - Зависит от: 1.1, 2.5

- [x] 2.7 [backend] Сделать сессионную cookie безопасной по умолчанию
  - Проверка: без `COOKIE_SECURE` cookie получает `Secure`, локальный Compose явно задает `COOKIE_SECURE=false`, тесты покрывают оба режима
  - Зависит от: 2.4

## 3. Роли и начальная настройка администратора

- [x] 3.1 [backend] Добавить команду `go run ./cmd/admin create` для начальной настройки учетной записи администратора
  - Проверка: команда запрашивает учетные данные, создает администратора с хешем пароля, повторный запуск не создает дубликат, публичная регистрация не выдает роль `admin`
  - Зависит от: 1.3

- [x] 3.2 [backend] Реализовать проверку текущей серверной сессии и возврат роли учетной записи для защищенных запросов
  - Проверка: запрос с действующей сессией возвращает пользователя и роль, запрос без действующей сессии получает отказ
  - Зависит от: 2.3

- [x] 3.3 [backend] Ограничить начальную настройку одной учетной записью администратора
  - Проверка: PostgreSQL атомарно допускает только одну роль `admin`, повтор команды с тем же или другим email не создает и не изменяет учетную запись, параллельные попытки не создают двух администраторов
  - Зависит от: 3.1

## 4. Пользовательские формы

- [x] 4.1 [frontend] Добавить русскоязычную форму регистрации с именем, фамилией, проверкой email, требованиями к длине пароля и единым отображением ошибок API
  - Проверка: пользователь видит ошибки `invalid_email`, `invalid_first_name`, `invalid_last_name`, занятого email и `invalid_password`, frontend разрешает `+`, не ломает вставку и автозаполнение и использует те же границы имени, фамилии, email и пароля, успешная регистрация открывает авторизованную часть приложения
  - Зависит от: 1.1, 2.1

- [x] 4.2 [frontend] Добавить русскоязычную форму входа и восстановление состояния текущей сессии при открытии приложения
  - Проверка: корректный вход открывает авторизованную часть, неверные учетные данные показывают общую ошибку, перезагрузка сохраняет действующую сессию
  - Зависит от: 1.1, 2.2, 3.2

## 5. Интеграционная проверка

- [x] 5.1 [backend] Добавить интеграционные тесты API регистрации, входа, истечения сессии и назначения ролей
  - Проверка: тесты по HTTP подтверждают сохранение и возврат имени и фамилии, ошибки пустых и слишком длинных значений, повторный email, общую ошибку входа, таймауты сессии, роль `user` и отдельную начальную настройку `admin`
  - Зависит от: 2.4, 2.5, 3.1, 3.2

- [x] 5.2 [infra] Настроить Docker Compose окружение для совместного запуска web, API, PostgreSQL и интеграционных тестов
  - Проверка: одной документированной командой поднимаются зависимости, применяются миграции, API ожидает готовность PostgreSQL, тесты получают корректные адреса и секреты через переменные окружения
  - Зависит от: 1.2, 5.1

- [x] 5.3 [infra] Добавить автоматический тестовый сценарий чистого запуска с подготовкой базы и начальной настройкой администратора
  - Проверка: запуск с чистой базой проходит без ручного SQL, команда `go run ./cmd/admin create` создает администратора, повторный запуск не создает дубликат, после завершения тестов окружение удаляется
  - Зависит от: 3.1, 5.2

- [x] 5.4 [infra] Обновить Compose и документацию для API namespace, trusted proxy и bootstrap-переменных
  - Проверка: Vite проксирует только `/api`, Compose передает API конфигурацию доверенного прокси и явно отключает `Secure` только локально, `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_FIRST_NAME` и `ADMIN_LAST_NAME` доходят до команды, README описывает фактические адреса и параметры
  - Зависит от: 1.1, 2.6, 2.7, 3.3, 5.2

- [x] 5.5 [infra] Расширить интеграционный сценарий проверками обновленного контракта и настроек безопасности
  - Проверка: `make auth-test` проверяет `/api/auth/*`, отсутствие старых маршрутов, независимые лимиты за прокси, единственного администратора и передачу bootstrap-переменных; `make check` и проверка актуальности генерации проходят
  - Зависит от: 2.6, 2.7, 3.3, 5.4
