## Purpose

Авторизация нужна, чтобы пользователь мог создать учетную запись с именем и фамилией и входить в систему по email и паролю. Возможность включает регистрацию, вход, серверную сессию и роли гостя, пользователя и администратора. Управление проектами и другие функции продукта в эту возможность не входят. Также не входят подтверждение email, восстановление пароля, OAuth, корпоративный вход, выход и управление пользователями администратором.

**User story:** Как пользователь платформы, я хочу зарегистрироваться и входить по email и паролю, чтобы получить доступ к функциям для зарегистрированных пользователей.

## ADDED Requirements

### Requirement: Регистрация пользователя

`POST /api/auth/register` MUST создавать учетную запись с ролью `user` по уникальным email, имени, фамилии и паролю.

Тело запроса регистрации MUST соответствовать контракту OpenAPI `RegisterRequest` и содержать обязательные поля `email`, `firstName`, `lastName` и `password`.

**Ограничения:**

- Email очищается от пробелов по краям и ограничивается длиной 254 символа после нормализации.
- API каноникализирует email: приводит local-part и ASCII-представление домена после IDNA-нормализации к нижнему регистру. Символ `+` сохраняется и не используется для удаления суффикса.
- API возвращает код `invalid_email` для некорректного адреса.
- Frontend после удаления пробелов по краям использует стандартный валидатор `z.email()` из Zod 4. Frontend не дублирует серверную IDNA-нормализацию и не считается источником истины для проверки email.
- Имя обязательно, очищается от пробелов по краям и должно содержать от 1 до 100 символов без управляющих символов. API возвращает код `invalid_first_name` при нарушении правила.
- Фамилия обязательна, очищается от пробелов по краям и должна содержать от 1 до 100 символов без управляющих символов. API возвращает код `invalid_last_name` при нарушении правила.
- Пароль должен содержать от 12 до 128 символов.
- Пароль не хранится в открытом виде. Система сохраняет хеш Argon2id с параметрами `m=65536 KiB`, `t=3`, `p=1`, 16-байтной солью и 32-байтным результатом в самодостаточном формате, содержащем алгоритм и параметры.
- Повторная регистрация с уже занятым каноническим email отклоняется без создания второй учетной записи.
- При нарушении правил пароля API возвращает код ошибки `invalid_password` и сообщение с требованием к длине. Frontend показывает это сообщение без собственных отличающихся правил.
- Клиент не может передать роль или получить при регистрации роль `admin`.
- Запросы регистрации ограничиваются по частоте.

#### Scenario: Успешная регистрация

- **КОГДА** гость отправляет уникальные email, имя, фамилию и пароль
- **ТОГДА** система создает учетную запись с ролью `user`, сохраняет имя и фамилию и устанавливает авторизованную серверную сессию

#### Scenario: Пустое имя

- **КОГДА** гость отправляет регистрацию без имени или с именем, состоящим только из пробелов
- **ТОГДА** API отклоняет запрос с кодом `invalid_first_name` и не создает учетную запись

#### Scenario: Слишком длинное имя

- **КОГДА** гость отправляет регистрацию с именем длиннее 100 символов
- **ТОГДА** API отклоняет запрос с кодом `invalid_first_name` и не создает учетную запись

#### Scenario: Пустая фамилия

- **КОГДА** гость отправляет регистрацию без фамилии или с фамилией, состоящей только из пробелов
- **ТОГДА** API отклоняет запрос с кодом `invalid_last_name` и не создает учетную запись

#### Scenario: Слишком длинная фамилия

- **КОГДА** гость отправляет регистрацию с фамилией длиннее 100 символов
- **ТОГДА** API отклоняет запрос с кодом `invalid_last_name` и не создает учетную запись

#### Scenario: Слишком короткий пароль

- **КОГДА** гость отправляет регистрацию с паролем длиной менее 12 символов
- **ТОГДА** API отклоняет запрос с кодом `invalid_password` и не создает учетную запись

#### Scenario: Слишком длинный пароль

- **КОГДА** гость отправляет регистрацию с паролем длиной более 128 символов
- **ТОГДА** API отклоняет запрос с кодом `invalid_password` и не создает учетную запись

#### Scenario: Некорректный email

- **КОГДА** гость отправляет регистрацию с email `user..name@example.com`
- **ТОГДА** API отклоняет запрос с кодом `invalid_email` и не создает учетную запись

#### Scenario: Повторный канонический email

- **ДАНО** учетная запись с email `user@example.com` уже существует
- **КОГДА** гость отправляет регистрацию с email ` USER@EXAMPLE.COM `
- **ТОГДА** система отклоняет запрос и не создает новую учетную запись

#### Scenario: Попытка назначить роль

- **КОГДА** гость отправляет регистрацию с полем роли `admin`
- **ТОГДА** система отклоняет назначение роли `admin`, а созданная учетная запись не получает права администратора

### Requirement: OpenAPI-контракт авторизации

API MUST публиковать OpenAPI-контракты для `POST /api/auth/register`, `POST /api/auth/login` и `GET /api/auth/me`.

OpenAPI MUST задавать базовый путь `/api`. Пути операций внутри контракта MUST оставаться ресурсными: `/auth/register`, `/auth/login` и `/auth/me`.

Контракт `RegisterRequest` MUST содержать обязательные строковые поля `email`, `firstName`, `lastName` и `password`. Контракты успешного ответа регистрации, входа и текущей сессии MUST возвращать пользователя с полями `id`, `email`, `firstName`, `lastName` и `role`, но не пароль и не его хеш.

Ошибки MUST использовать единый формат с машинно-читаемым кодом. Для ошибок имени и фамилии используются коды `invalid_first_name` и `invalid_last_name`.

#### Scenario: Успешная регистрация по OpenAPI-контракту

- **КОГДА** клиент отправляет `POST /api/auth/register` с полями `email`, `firstName`, `lastName` и `password`
- **ТОГДА** API возвращает пользователя с полями `id`, `email`, `firstName`, `lastName` и `role` и не возвращает пароль или его хеш

#### Scenario: Получение текущего пользователя

- **КОГДА** авторизованный клиент отправляет `GET /api/auth/me`
- **ТОГДА** API возвращает текущего пользователя с именем, фамилией и ролью

### Requirement: Вход пользователя

`POST /api/auth/login` MUST проверять email и пароль и создавать серверную сессию только для действующей учетной записи.

**Ограничения:**

- Email сравнивается по каноническому значению без учета регистра.
- Имя и фамилия возвращаются в данных текущего пользователя после успешного входа.
- При неверном email или пароле система возвращает одну и ту же ошибку без раскрытия того, существует ли учетная запись.
- Попытки входа ограничиваются по частоте.

#### Scenario: Успешный вход

- **ДАНО** зарегистрированная учетная запись с корректным паролем
- **КОГДА** пользователь отправляет корректные email и пароль
- **ТОГДА** система создает серверную сессию и возвращает роль пользователя

#### Scenario: Неверный пароль

- **ДАНО** зарегистрированная учетная запись
- **КОГДА** пользователь отправляет неверный пароль
- **ТОГДА** система отклоняет вход с общей ошибкой учетных данных и не создает сессию

### Requirement: Ограничение частоты запросов авторизации

API MUST ограничивать частоту регистрации и входа без общего счетчика для всех пользователей за reverse proxy.

**Ограничения:**

- API определяет клиентский IP из заголовков прокси только для адресов, перечисленных в конфигурации доверенных прокси.
- Ограничение входа учитывает клиентский IP и канонический email.
- Прямой клиент не может подменить свой IP заголовком forwarded IP.
- Сервер удаляет истекшие счетчики и не накапливает их без границы.
- Правила подключаются к операциям авторизации, а не определяются сравнением строк URL.

#### Scenario: Независимые попытки входа за одним прокси

- **ДАНО** два пользователя обращаются к API через один доверенный reverse proxy
- **КОГДА** первый пользователь исчерпывает свой лимит попыток входа
- **ТОГДА** второй пользователь сохраняет возможность входа со своим email

#### Scenario: Недоверенный forwarded IP

- **КОГДА** прямой клиент отправляет заголовок forwarded IP без доверенного прокси
- **ТОГДА** API использует сетевой адрес клиента и игнорирует заголовок

### Requirement: Сессионная cookie

Серверная сессия MUST передаваться через cookie с атрибутом `HttpOnly`, а в сетевом окружении также с атрибутом `Secure`. Конфигурация по умолчанию MUST включать `Secure`; локальное окружение без TLS отключает его явно.

**Общие соглашения:**

- Сервер хранит состояние сессии на стороне сервера.
- Сессия истекает после 14 дней бездействия или через 30 дней с момента создания, даже если пользователь активен.
- Клиент не получает пароль или его хеш.
- Защищенные запросы используют текущую сессию для определения пользователя и его роли.
- Изменяющие запросы защищаются от CSRF.

#### Scenario: Защищенный запрос без сессии

- **КОГДА** гость отправляет запрос к операции, доступной только зарегистрированному пользователю
- **ТОГДА** система отклоняет запрос как неавторизованный

### Requirement: Роль учетной записи

Система MUST присваивать и возвращать роль учетной записи `user` или `admin` на серверной стороне.

**Ограничения:**

- Публичный API регистрации всегда создает учетную запись с ролью `user`.
- Учетная запись `admin` создается только при начальной настройке отдельной командой `go run ./cmd/admin create`.
- Система допускает не более одной учетной записи с ролью `admin`; ограничение обеспечивается атомарно в PostgreSQL.
- Повторный запуск команды с любым email не создает второго администратора и завершается без раскрытия или замены учетных данных существующего администратора.
- Команда запрашивает email и пароль администратора интерактивно или получает их через защищенные секреты конфигурации.
- Compose передает команде явно заданные переменные `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_FIRST_NAME` и `ADMIN_LAST_NAME`.
- Пароль администратора сохраняется в базе только в виде стойкого хеша.
- Публичный API регистрации не создает и не назначает роль `admin`.

#### Scenario: Регистрация получает роль пользователя

- **КОГДА** гость успешно завершает регистрацию
- **ТОГДА** система сохраняет за учетной записью роль `user`

#### Scenario: Начальная настройка администратора

- **КОГДА** оператор один раз выполняет команду `go run ./cmd/admin create` и передает учетные данные администратора
- **ТОГДА** система создает одну учетную запись с ролью `admin`, сохраняя пароль только в виде стойкого хеша

#### Scenario: Повторная начальная настройка с другим email

- **ДАНО** учетная запись администратора уже существует
- **КОГДА** оператор повторно выполняет команду с другим email
- **ТОГДА** система не создает второго администратора и не изменяет существующую учетную запись
