# case-01-robotic-solutions-platform-team-2

Проект использует упрощенную конфигурацию OpenSpec для Codex и Claude Code. Источник: [custom-openspec](https://github.com/shinokamix/custom-openspec).

## Подготовьте OpenSpec

Установите [Node.js 20.19.0 или новее](https://nodejs.org/en/download), затем установите OpenSpec CLI:

```bash
npm install -g @fission-ai/openspec@latest
```

Проверьте установку:

```bash
openspec --version
```

После клонирования репозитория дополнительная настройка не нужна. Конфигурация, схема и скиллы агентов уже находятся в проекте.

## Рабочий процесс

Каждое изменение проходит три фазы. Завершите текущую фазу перед переходом к следующей.

### 1. Согласуйте поведение и план

Попросите агента подготовить изменение. Укажите цель и границы работы:

```text
Подготовь изменение: <цель и границы>
```

Явный вызов скилла не нужен. Если вы хотите вызвать его напрямую, используйте:

```text
Codex:       $openspec-propose <описание изменения>
Claude Code: /openspec-propose <описание изменения>
```

Агент выберет имя изменения на английском языке в `kebab-case`. Затем он создаст артефакты и выполнит строгую проверку OpenSpec. Используйте это имя в следующих фазах.

Проверьте два результата:

- `openspec/changes/<имя>/specs/**/*.md` описывает требования, сценарии и общие контракты.
- `openspec/changes/<имя>/tasks.md` описывает порядок реализации, владельца и проверку каждой задачи.

До начала реализации проверьте артефакты вместе с командой:

- Ясно ли описаны результат и границы изменения?
- Можно ли проверить каждое требование по сценарию?
- Содержит ли каждый сценарий конкретное действие и наблюдаемый результат?
- Есть ли у каждой задачи один владелец, проверка и явные зависимости?

Если план требует правок, обновите активное изменение до начала реализации. Пример запроса:

```text
Обнови спецификации и задачи изменения <имя>: <нужная правка>. Не начинай реализацию. После правок выполни строгую проверку OpenSpec.
```

Переходите к реализации только после согласования артефактов.

### 2. Реализуйте согласованное изменение

Попросите агента реализовать изменение:

```text
Реализуй изменение <имя>
```

Явный вызов скилла не нужен. Если вы хотите вызвать его напрямую, используйте имя из первой фазы:

```text
Codex:       $openspec-apply-change <имя>
Claude Code: /openspec-apply-change <имя>
```

Без дополнительных ограничений агент выполнит все незавершенные задачи. Чтобы задать скоуп, перечислите нужные задачи:

```text
Реализуй только задачи 1.2 и 1.3 из изменения <имя>
```

Если выбранная задача зависит от другой незавершенной задачи, добавьте зависимость в скоуп. После каждой задачи агент запускает указанную проверку. Успешно проверенные задачи он отмечает в `tasks.md`.

Если реализация требует изменить поведение, общий контракт или обязательный объем, агент останавливается. В таком случае вернитесь к первой фазе, обновите артефакты и снова согласуйте их. Не просите агента обходить расхождение в коде.

Чтобы продолжить частичную реализацию, повторите запрос. Снова укажите скоуп, если хотите ограничить работу.

### 3. Сохраните итоговые требования

После завершения всех задач и проверок попросите агента архивировать изменение:

```text
Архивируй изменение <имя>
```

Явный вызов скилла не нужен. Если вы хотите вызвать его напрямую, используйте:

```text
Codex:       $openspec-archive-change <имя>
Claude Code: /openspec-archive-change <имя>
```

Агент проверяет изменение, обновляет основные спецификации в `openspec/specs/` и переносит рабочие файлы в `openspec/changes/archive/`. После этого изменение исчезает из списка активных.

Архивируйте изменение в той же ветке, что и код. Так код и действующие требования попадут в репозиторий вместе.

## Используйте эти правила в ежедневной работе

- Одно изменение должно давать один связный результат для пользователя или системы.
- Спецификации описывают поведение, которое видит пользователь или другая система. Детали реализации находятся в `tasks.md`.
- Каждый сценарий должен иметь наблюдаемый результат. Каждый пункт плана должен иметь проверку.
- Измените артефакты до кода, если договоренности поменялись.
- Не закрывайте задачу после частичной реализации или неуспешной проверки.
- Не архивируйте изменение, пока в `tasks.md` остались незавершенные задачи.

Повторяйте этот цикл для каждого изменения: согласуйте, реализуйте, архивируйте.

## Как устроена конфигурация

OpenSpec хранит проектную конфигурацию, схему и рабочие артефакты в каталоге `openspec/`:

```text
openspec/
├── config.yaml
├── schemas/spec-driven/
│   ├── schema.yaml
│   └── templates/
│       ├── spec.md
│       └── tasks.md
├── changes/
│   └── archive/
└── specs/
```

- `openspec/config.yaml` выбирает схему `spec-driven`. В этот файл можно добавить контекст проекта, правила для отдельных артефактов и указания для операций `apply` и `archive`.
- `openspec/schemas/spec-driven/schema.yaml` описывает жизненный цикл изменения. Схема требует сначала создать `specs/**/*.md`, затем `tasks.md`. Она также задает формат артефактов, зависимости между ними, правила проверки и порядок реализации.
- `openspec/schemas/spec-driven/templates/spec.md` содержит исходную структуру спецификации.
- `openspec/schemas/spec-driven/templates/tasks.md` содержит исходную структуру плана с владельцем, проверкой и зависимостями каждой задачи.
- `openspec/changes/<имя>/` хранит активное изменение. В нем находятся спецификации изменения, `tasks.md` и служебный файл `.openspec.yaml`.
- `openspec/specs/` хранит действующие требования проекта.
- `openspec/changes/archive/` хранит завершенные изменения после архивации.

Инструкции агентов находятся в `.agents/skills/`. Они описывают подготовку, реализацию и архивацию изменения. `.claude/skills/` содержит символические ссылки на эти файлы, поэтому Codex и Claude Code используют общие инструкции.
