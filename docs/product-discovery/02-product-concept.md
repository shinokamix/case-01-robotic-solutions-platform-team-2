# Концепция продукта

## Проблема

Компании вручную собирают сведения о роботах, проверяют ограничения и считают экономику. Данные поставщиков трудно сравнивать, а часть характеристик отсутствует или не имеет проверяемого источника.

Платформа должна сократить путь от исходных параметров объекта до обоснованной гипотезы о пилоте.

## Пользователи

| Роль | Задача |
| --- | --- |
| Гость | Пройти демонстрационный расчет |
| Пользователь | Оценить свой объект и сравнить сценарии |
| Администратор | Поддерживать каталог, нормативы и версии |
| Вендор | Предлагать изменения продукта после MVP |

Основной пользователь готовит предварительное обоснование роботизации для руководства, технической команды или поставщика.

## Пользовательский путь

1. Пользователь выбирает тип объекта.
2. Пользователь вводит параметры вручную или загружает файл.
3. Платформа проверяет типы, единицы, диапазоны и обязательные поля.
4. Правила отклоняют несовместимые решения.
5. Платформа ранжирует остальные решения и объясняет результат.
6. Пользователь сравнивает текущий процесс, покупку и RaaS.
7. Платформа рассчитывает состав оборудования и экономику.
8. Пользователь меняет допущения и сравнивает результаты.
9. Имитация показывает производительность и узкие места.
10. Пользователь сохраняет проект и выгружает PDF.

Ошибка импорта не должна менять сохраненный проект. Повторное открытие проекта должно давать тот же результат.

## Граница MVP

MVP полностью поддерживает внутрискладское перемещение паллет.

В полный сценарий входят:

- ручной ввод и импорт параметров.
- локальный каталог.
- технический отсев.
- объяснимое ранжирование.
- текущий процесс, покупка и фиксированный RaaS.
- CAPEX, OPEX, TCO, годовой эффект, срок окупаемости и ROI.
- анализ чувствительности по трем параметрам.
- детерминированная 2D-имитация.
- сохранение проекта и PDF-отчет.

Для аэропорта и медицинского учреждения MVP содержит отдельные формы и подбор типов решений. Полная экономика и имитация для этих объектов не входят в MVP.

После MVP можно добавить табличный экспорт, промышленные интеграции, другие схемы RaaS, кредит, лизинг, роль вендора и ML-ранжирование.

## Подбор решений

Подбор состоит из двух этапов.

Сначала правила проверяют критические ограничения:

- грузоподъемность.
- габариты и ширину прохода.
- пол и рабочую температуру.
- зарядную инфраструктуру.
- тип груза и операции.
- обязательные интеграции.
- требуемую производительность.

Затем балльная модель ранжирует решения, которые правила не отклонили. Высокий балл не может скрыть нарушение критического ограничения.

Результат получает один статус:

- `applicable` означает, что правила пройдены по подтвержденным данным.
- `applicable_with_assumptions` означает, что правила пройдены с сохраненными допущениями.
- `needs_review` означает, что данных недостаточно.
- `not_applicable` означает, что нарушено критическое правило.

Решение со статусом `needs_review` остается в выдаче, но не считается подтвержденным.

Платформа показывает сработавшие правила, недостающие данные, допущения, вклад критериев и источники значений.

## Экономика

Backend рассчитывает финансовые показатели. Frontend только показывает результат.

Расчет включает:

- количество роботов с учетом производительности, загрузки и резерва.
- CAPEX по оборудованию, инфраструктуре, ПО, интеграции, запуску, обучению и резерву.
- OPEX по сервису, лицензиям, энергии, связи, ремонту и персоналу.
- годовой эффект.
- простой срок окупаемости.
- ROI.
- TCO за пять лет.

MVP сравнивает:

| Сценарий | Основные расходы |
| --- | --- |
| Текущий процесс | Персонал и текущая эксплуатация |
| Покупка | Оборудование, внедрение и обслуживание |
| Фиксированный RaaS | Разовый платеж за запуск и ежемесячная плата за робота |

При `CAPEX = 0` ROI и срок окупаемости не рассчитываются. Платформа показывает годовой эффект, TCO и накопленный эффект.

Анализ чувствительности меняет цену оборудования, объем операций и стоимость труда.

## Имитация

MVP использует дискретно-событийную модель и параметрическую 2D-схему склада. Полная физическая модель и 3D не требуются.

Модель учитывает зоны, маршруты, задания, роботов, точки загрузки, зарядные станции, очереди и смены. Она возвращает выпуск, загрузку, простои, очередь и незавершенные задания.

Одинаковые входные данные и `seed` должны давать одинаковый результат. Скорость анимации меняет только отображение.

Если имитация не достигает планового объема, платформа показывает расхождение. Пользователь сам запускает пересчет состава оборудования.

## Данные и версии

Каталог хранит продукт отдельно от его применимости, предложения и кейса. Каждая важная характеристика содержит источник, дату и статус проверки.

Проект хранит версии:

- параметров объекта.
- каталога.
- правил подбора.
- экономических формул.
- модели имитации.

Опубликованная версия не изменяется. Новые данные создают новую версию.

## Роль ML

Основной путь MVP работает без ML. Критические ограничения всегда проверяют правила.

До подготовки размеченной выборки ML можно использовать для семантического поиска, нормализации категорий и извлечения кандидатов ТТХ. Человек должен проверять извлеченные значения.

После появления данных ML может менять порядок допустимых кандидатов. Модель не должна скрывать решение или рассчитывать финансовый результат.

## Технические границы

- Frontend использует React, TypeScript и Vite+ без SSR.
- Backend представляет собой модульный монолит на Go.
- PostgreSQL хранит проекты, каталог и версии.
- OpenAPI задает контракт между frontend и backend.
- Docker Compose запускает локальную демонстрацию.
- Внешние сайты не являются обязательной частью демонстрации.
- API проверяет владельца проекта.
- Экономический расчет завершается за 10 секунд.
- Имитация завершается за 60 секунд.
- Основной язык интерфейса: русский.
- Минимальное разрешение: 1366 на 768 пикселей.

Конкретные библиотеки, структура репозитория, CI и схема деплоя определяются во время проектирования и не входят в discovery.
