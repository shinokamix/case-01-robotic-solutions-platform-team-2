# Решения и дорожная карта

Документ фиксирует решения команды, границы продукта и порядок реализации. Решения и roadmap находятся в одном файле. Подробные требования организатора описаны в [требованиях и продуктовой рамке](02-requirements-and-product-frame.md), а данные и их ограничения в [выжимке исходных материалов](01-artifact-summary.md).

## Как читать документ

Статус определяет, можно ли переносить решение в спецификацию:

- `Подтверждено` означает, что решение принято.
- `Рабочее предложение` означает, что команда использует решение для планирования, но должна подтвердить его до реализации.
- `Нужен ответ` означает, что вопрос закрыт временным допущением. Владелец должен заменить его подтвержденным решением.

Открытый вопрос может не блокировать разработку. Он блокирует приемку результата, если влияет на этот результат. Допущения, которые меняют расчет, показываем в интерфейсе и отчете.

## Технические границы

### Репозиторий и ответственность

```text
apps/
  web/                  # React, TypeScript, Vite Plus
  api/                  # Go API, расчеты, доступ к PostgreSQL
    migrations/
  data/                 # Python, подготовка и проверка данных
packages/
  contracts/            # OpenAPI, схемы данных, примеры запросов и ответов
artifacts/              # Неизменные материалы организатора
docs/
openspec/
compose.yaml
README.md
```

| Часть | Отвечает за | Не отвечает за |
| --- | --- | --- |
| `apps/web` | Формы, каталог, сравнение, расчеты и 2D-визуализацию | Финансовые формулы и правила подбора |
| `apps/api` | Проверку входов, подбор, расчеты, проекты, роли, каталог, имитацию и экспорт | Обращение к внешним источникам во время демонстрационного расчета |
| `apps/data` | Чтение исходных файлов, очистку, нормализацию, проверку и подготовку импорта | Запуск основного пользовательского пути и обучение моделей |
| `packages/contracts` | OpenAPI, схемы данных, коды параметров и единицы | Общую бизнес-логику для разных языков |

`apps/data` запускается отдельно. Скрипты готовят файлы для импорта через Go API. API проверяет данные перед импортом. Для работы приложения Python не требуется. Если появится отдельная задача обучения моделей, для нее можно добавить `apps/ml`.

Go рассчитывает экономику. Имитация использует тот же состав оборудования и параметры производительности, но моделирует операции во времени. Web показывает состояние имитации и KPI. Проверка расхождения между расчетом и имитацией сравнивает разные результаты, а не дублирует одно число.

### Общие правила

- API описывается в OpenAPI. Изменение запроса или ответа начинается с обновления контракта и примеров.
- Backend проверяет все входы. Проверки формы помогают пользователю, но не заменяют серверную проверку.
- Коды параметров и единицы совпадают в подготовленных данных, API и интерфейсе. Проценты из исходных файлов преобразуются явно.
- Секреты не хранятся в репозитории. В конфигурации для запуска используются только примеры без секретов.
- Docker Compose запускает web, API и PostgreSQL. Python запускается отдельно, когда меняются данные.
- CI проверяет сборку, форматирование, расчетные тесты и соответствие демонстрационных данных схемам.
- Новые типы объектов добавляются через параметры и применимость. Новые расчетные модули добавляются в Go. Универсального конструктора правил не будет.

Конкретные библиотеки, таблицы БД и команды CI уточняются в задачах реализации.

## Дорожная карта

Порядок реализации идет от рабочего складского расчета к возможностям конкурсного MVP. Каждый срез дает пользовательский результат, который можно проверить через интерфейс.

| Этап | Результат |
| --- | --- |
| `PRE-01` | Пользователь создает, сохраняет и повторно открывает складской проект. |
| `PRE-02` | Администратор управляет данными, которые нужны расчету. |
| `PRE-03` | Пользователь получает объяснимый подбор продуктов. |
| `PRE-04` | Пользователь сравнивает текущий процесс с покупкой оборудования. |
| `MVP-02` | Пользователь сравнивает продукты, покупку и RaaS. |
| `MVP-03` | Пользователь загружает данные по CSV-шаблону. |
| `MVP-04` | Пользователь запускает связанную с расчетом 2D-имитацию. |
| `MVP-05` | Пользователь выгружает расчет и визуализацию. |
| `MVP-06` | Пользователь открывает демонстрационный сценарий для другого типа объекта. |
| `MVP-07` | Проверяющий запускает систему и повторяет демонстрацию без помощи разработчика. |

Срезы реализуются как отдельные изменения OpenSpec с контрактами, задачами и проверкой результата. Не нужно сначала описывать весь MVP. Сначала команда подтверждает границы pre-MVP и набор данных, затем реализует четыре pre-MVP-среза по порядку.

## Pre-MVP

### Цель и границы

Pre-MVP отвечает на вопрос: может ли пользователь на одном складском наборе получить объяснимый подбор оборудования для перемещения паллет, оценить количество роботов и сравнить текущий процесс с покупкой?

Модель использует один маршрут между двумя заданными зонами. Она учитывает рейс с грузом, возврат, погрузку, разгрузку, рабочее время и явно заданные коэффициенты. Она не моделирует весь склад, комплектацию заказов, взаимодействие разных парков или оптимизацию маршрутов.

В pre-MVP входят все CRUD, необходимые конкурсному MVP, роли и административные формы. В него не входят имитация, RaaS, пользовательский файловый импорт и экспорт. Эти функции реализуются в MVP.

### Данные и права доступа

| Область | Возможности pre-MVP | Доступ |
| --- | --- | --- |
| Проекты | Создание, список, просмотр, изменение, сохранение, повторное открытие, копирование и удаление | Пользователь работает только со своими проектами |
| Сценарии | Создание, просмотр, изменение, удаление, сохранение входов и результатов | Владелец проекта. В pre-MVP доступны текущий процесс и покупка |
| Каталог | CRUD продуктов, характеристик, применимости, предложений и кейсов | Администратор изменяет. Гость и пользователь просматривают опубликованные данные |
| Справочники | CRUD отраслей, типов объектов, процессов, решений и определений параметров | Администратор |
| Нормативы | CRUD значений, единиц, области применения и источников | Администратор |
| Источники | CRUD ссылок, описаний, дат и статусов подтверждения | Администратор |

Гость открывает каталог и демонстрационный расчет без сохранения чувствительных данных. Пользователь управляет своими проектами. Администратор управляет общими данными. Backend проверяет права доступа.

Регистрация принимает email и пароль. Новый аккаунт получает роль пользователя. Регистрация не позволяет назначить роль администратора. Администратор создается при начальной настройке. Нужны уникальные email, стойкие хеши паролей, серверная сессия и HttpOnly cookie. В сетевом окружении cookie использует `Secure`.

Изменяющие запросы защищаются от CSRF. Попытки входа и регистрации ограничиваются по частоте. Подтверждение email, восстановление пароля, OAuth и административный CRUD пользователей не входят в эту версию.

Связанные записи редактируются внутри карточек. Удаление используемой записи справочника или источника блокируется с объяснением. Изменение каталога не меняет сохраненные расчеты. Удаление проекта удаляет его сценарии и связанные файлы после появления загрузки в MVP.

CRUD справочников поддерживает все типы объектов. В pre-MVP расчетом проверяется только выбранный складской процесс. Изменение определения параметра не создает расчетную формулу автоматически.

### Минимальная подготовка данных

Для первого расчета не нужно обогащать все 223 строки каталога или строить универсальный импорт.

1. Выбрать один складской набор из материалов организатора и сохранить связь каждого параметра с исходной строкой.
2. Описать объем и интенсивность операций, режим работы, массу и габариты паллеты, длину маршрута, ограничения прохода и пола, численность и стоимость труда.
3. Задать недостающие времена операций и нормативы отдельными допущениями.
4. Назначить параметрам стабильные коды, типы, единицы, обязательность и диапазоны. Проценты преобразовать явно.
5. Выбрать от двух до трех продуктов и подтвердить их применимость к выбранной операции. Название категории не подтверждает применимость.
6. Дополнить только нужные характеристики: грузоподъемность, массу и габариты оборудования, скорость или производительность, ограничения, автономность, зарядку, цену и состав предложения.
7. Для каждого значения сохранить источник, дату и статус. Допущение хранить отдельно от подтвержденного значения. Отсутствующую цену не заменять нулем.
8. Сохранить исходный `id`, номер строки и собственный ключ каждой строки. Повторы не объединять автоматически и не усреднять цены.
9. Подготовить повторяемую загрузку демонстрационного набора. Ошибки подготовки должны быть видны до запуска демо.

Если для выбранного процесса нельзя подтвердить характеристики хотя бы одного продукта, подбор не принимается. Формулы можно проверить на синтетических данных, но нельзя выдавать их за результат на каталожном продукте.

### Пользовательский путь

1. Гость открывает демонстрационный склад с заполненной формой.
2. Пользователь меняет объем операций, параметры груза, маршрут, режим работы и стоимость труда.
3. Система показывает единицы, значения по умолчанию, источники и ошибки ввода.
4. Пользователь запускает подбор и видит причины соответствия, исключения и необходимости проверки.
5. Пользователь выбирает продукт и видит количество роботов, производительность, CAPEX, годовой OPEX, эффект, срок окупаемости, ROI и TCO за пять лет.
6. Пользователь сравнивает текущий процесс и покупку, видит состав затрат и допущения, затем меняет параметр и получает пересчет.
7. Пользователь входит в систему, сохраняет проект, открывает его после нового входа, копирует и удаляет копию.

Экономия рабочего времени показывается отдельно от денежной экономии. Высвобожденные часы и FTE не означают сокращение расходов без отдельного допущения.

### Критерии завершения pre-MVP

Pre-MVP завершен, когда:

- пользователь проходит весь путь через интерфейс без ручного редактирования файлов;
- все CRUD из таблицы работают через формы и API и сохраняются после перезапуска;
- регистрация, вход, выход, роли и изоляция проектов проверены;
- работают повторное открытие, изменение, копирование и удаление проекта;
- хотя бы один реальный продукт имеет достаточно данных для выбранного процесса;
- источники и неподтвержденные допущения видны пользователю;
- одинаковые входы и версии дают одинаковый расчет;
- контрольный пример сходится в пределах записанного допуска;
- проверены пустая выдача, недостающая цена, нулевой CAPEX и неположительный эффект;
- команда зафиксировала данные и допущения, которые нужно уточнить до конкурсной сдачи.

Имитация, RaaS, файловый импорт и экспорт не являются условиями завершения pre-MVP.

## Конкурсный MVP

### Граница MVP

MVP выполняет обязательные требования ТЗ. Ограничение объема достигается глубиной реализации и небольшим демонстрационным каталогом, а не удалением обязательных ролей, импорта или отчетов.

| Область | Реализация MVP | Ограничение |
| --- | --- | --- |
| Объекты | Склад, аэропорт и медицинское учреждение с формами и демонстрационными решениями | Полный расчетный путь есть только для выбранного складского процесса |
| Ввод | Ручной ввод и CSV-шаблон с обязательными полями, типами, единицами, диапазонами и источниками | Один версионированный шаблон на тип объекта |
| Каталог | Данные организатора, нужные ТТХ, поиск, фильтрация, сортировка и сравнение | Обогащаем только демонстрационные процессы |
| Подбор | Отсев, ранжирование, объяснения, источники, недостающие данные и ручное добавление с предупреждением | Фиксированные документированные правила и веса |
| Экономика | Количество оборудования, CAPEX, OPEX, эффект, окупаемость, ROI и TCO минимум за пять лет | Покупка и фиксированный RaaS |
| Сценарии | Текущий процесс, покупка и RaaS, допущения, ручные корректировки и чувствительность | Без конструктора финансовых схем |
| Имитация | Зоны, маршруты, роботы, операции, зарядки, загрузка, простои и узкие места | Параметрическая 2D-схема без редактора планировки |
| Проекты | Создание, изменение, сохранение, открытие, копирование, удаление и воспроизведение | Один снимок состояния без истории каждого действия |
| Роли | Гость, пользователь и администратор | Без роли вендора, OAuth, восстановления пароля и корпоративного входа |
| Администрирование | Формы и документированные интерфейсы импорта каталога, справочников, нормативов и источников | Без автоматического парсинга сайтов |
| Экспорт | PDF, CSV расчетных таблиц и изображение визуализации | Один шаблон отчета |
| Запуск | Docker Compose, демо-данные, документация, презентация и сценарий проверки | Один демонстрационный стенд |

Складской процесс проходит путь от ручного ввода или импорта до подбора, сравнения, экономики, имитации, сохранения и экспорта. Для аэропорта и медицинского учреждения не показываем складскую экономику или складскую имитацию как их расчет.

### Правила функций MVP

- `eligible` означает соответствие проверенным ограничениям.
- `needs_review` означает, что данных для вывода не хватает.
- `excluded` означает известную несовместимость и имеет приоритет над неполнотой данных.
- Ручное добавление кандидата в сравнение не снимает предупреждение.
- RaaS использует фиксированную ежемесячную плату и явно заданные разовые затраты запуска. Состав услуг, продление и отсутствие реального тарифа отмечаются как допущения.
- Чувствительность показывает нижнее, базовое и верхнее значение для объема операций, стоимости труда и стоимости оборудования. Параметры меняются по одному.
- Вместе с проектом сохраняются входы, цены, характеристики, ручные изменения, допущения, версии формул и данных, `seed`, результат и дата.
- Имитация показывает операции, зарядки, загрузку, простои и узкие места. Ускорение воспроизведения не меняет модельное время и KPI.
- PDF и CSV используют тот же сохраненный результат, что и интерфейс. Отчет содержит параметры объекта, решения, оборудование, экономику, допущения, источники, ограничения и предупреждение о необходимости обследования.

### Вертикальные срезы MVP

| Срез | Пользовательский результат | Основная проверка |
| --- | --- | --- |
| `MVP-02` | Пользователь сравнивает продукты, текущий процесс, покупку и RaaS. | Сценарии используют общий объем работ, горизонт и состав затрат. Чувствительность и ручные корректировки видны. |
| `MVP-03` | Пользователь загружает параметры по CSV-шаблону. Администратор обновляет каталог и нормативы файлом. | Ошибка импорта не меняет сохраненный проект. Обновление каталога не меняет старый расчет. |
| `MVP-04` | Пользователь запускает 2D-имитацию и видит загрузку, простои и узкое место. | Недостаточный парк дает измеримый дефицит производительности. `seed` воспроизводит результат. |
| `MVP-05` | Пользователь выгружает расчет и визуализацию. | PDF, CSV и изображение совпадают с сохраненным состоянием проекта. |
| `MVP-06` | Пользователь открывает аэропорт или медицинское учреждение и видит соответствующие параметры и решения. | Система не выдает складскую модель за расчет другого объекта. |
| `MVP-07` | Проверяющий запускает систему и повторяет демонстрацию без помощи разработчика. | Чистый запуск, учетные записи, контрольный проект, документация, презентация и сценарий проверки доступны. |

`MVP-01` перенесен в `PRE-01` и `PRE-04`, потому что роли, CRUD и базовый расчет нужны до остальных функций.

### Критерии готовности MVP

MVP готов, когда:

- доступны три типа объектов и их демонстрационные наборы;
- складской путь проходит ввод или импорт, подбор, сравнение, экономику, имитацию, сохранение и экспорт;
- подбор объясняет включение, исключение, вклад факторов, источники и недостающие данные;
- текущий процесс, покупка и RaaS сравниваются по единой классификации затрат;
- работают ручные допущения, корректировки и чувствительность минимум по трем параметрам;
- проверены нулевые инвестиции, отрицательный эффект, пустая выдача и неполные данные;
- проект воспроизводится по сохраненным версиям данных, формул и `seed`;
- администратор управляет каталогом, справочниками, нормативами, значениями по умолчанию и источниками;
- PDF, CSV и изображение соответствуют одному состоянию проекта;
- чистое окружение запускается через Docker Compose по инструкции;
- проверены права гостя, пользователя и администратора;
- типовой расчет занимает не более 10 секунд, а запуск или пересчет имитации не более 60 секунд;
- интерфейс работает на русском языке при разрешении от 1366 × 768.

## Что не входит в MVP

- Обучение ML без размеченной выборки и отдельный ML-сервис ради наличия Python в стеке.
- Полная экономика и имитация всех процессов склада, аэропорта и медицинского учреждения.
- Обогащение всех строк каталога, автоматический сбор сайтов и обновление по расписанию.
- 3D, редактор планировки и оптимизация маршрутов.
- Интеграции с промышленными системами и государственными реестрами, а также расчет мер поддержки.
- Кредит, лизинг, сложные договоры RaaS и вероятностный анализ чувствительности.
- Роль вендора, корпоративный вход и сложное управление организациями.
- Микросервисы, брокер сообщений, кластерный деплой, универсальный конструктор правил и полная история изменений проектов.

## Материалы для сдачи

Pre-MVP сам по себе не является пакетом промежуточной сдачи. Для промежуточной проверки нужны репозиторий, инструкция запуска, доступный прототип или сборка, описание архитектуры и границ MVP, рабочий путь до подбора и предварительного расчета, черновая структура каталога и проекта, список реализованного, рисков и оставшихся задач.

Для финальной сдачи нужны:

- репозиторий и инструкция локального запуска или ссылка на прототип;
- презентация и документация;
- демонстрационные учетные записи, наборы данных, контрольный проект, сценарий проверки и пример отчета;
- описание аудитории, границ продукта, архитектуры и API;
- формулы, единицы, источники, допущения, логика подбора, RaaS и амортизация;
- руководства пользователя и администратора;
- описание возможных интеграций с WMS, ERP, 1С, мониторингом и аналитикой ФЦ БАС;
- ссылки на внешние библиотеки и источники, ограничения и план развития.

В презентации отдельно отмечаются полностью реализованные функции, частичные реализации и прототипы. Демонстрация на наборе организатора должна воспроизводиться в переданной версии.
