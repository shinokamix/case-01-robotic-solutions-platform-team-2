# Развернутое техническое задание на платформу подбора роботизированных решений

## 1. Назначение документа

Документ переводит конкурсное ТЗ в продуктовые границы и проверяемые группы требований. Это еще не OpenSpec и не план реализации. После согласования этой проработки требования будут разделены на отдельные спецификации возможностей продукта.

Основной источник требований — [техническое задание](../../artifacts/01-tz-platforma-podbora-robotizirovannyh-resheniy.pdf). [Дополнительные пояснения](../../artifacts/02-dopolnitelnye-poyasneniya-i-dopuscheniya-k-tz.pdf) уточняют трактовку, но не заменяют ТЗ. Файл [инструкции к Q&A](../../artifacts/03-lct-2026-sessiya-voprosov-i-otvetov.pdf) не содержит ответов по кейсу и не изменяет требования.

## 2. Проблема и продуктовый результат

### 2.1. Проблема

Предприятие, которое рассматривает роботизацию, вынуждено вручную собирать несопоставимые сведения о решениях, проверять техническую применимость, оценивать инфраструктуру, рассчитывать количество оборудования и строить экономику. Из-за неполноты данных и непрозрачности предпосылок решение о пилоте откладывается или принимается без достаточного обоснования.

### 2.2. Ожидаемый результат

Платформа должна за один последовательный сценарий сформировать предварительную оценку:

- какие решения технически применимы;
- какие ограничения исключают решение;
- какие данные отсутствуют и требуют проверки;
- сколько оборудования потребуется;
- сколько будут стоить покупка и эксплуатация;
- как роботизация изменит расходы и производительность;
- где модель показывает очереди, простои и узкие места;
- насколько результат чувствителен к ключевым допущениям.

### 2.3. Границы результата

Результат является предварительным и должен прямо содержать предупреждение о необходимости обследования объекта и верификации исходных данных. Платформа не выполняет инженерное проектирование, сертификацию, договорную оценку поставщика или финансовый аудит.

## 3. Целевая аудитория и роли

| Роль | Задача | Доступ |
| --- | --- | --- |
| Гость | Быстро понять возможности и пройти демонстрационный расчет | Каталог, демо-объекты, расчет без сохранения чувствительных данных |
| Пользователь | Оценить собственный объект и сравнить варианты | Проекты, импорт, подбор, экономика, имитация, экспорт |
| Администратор | Поддерживать данные и нормативы | Каталог, справочники, источники, версии моделей, параметры по умолчанию |
| Вендор | Предложить или уточнить продукт | Опциональная роль после MVP с обязательной модерацией |

Ключевой пользователь — специалист, который готовит предварительное обоснование проекта роботизации для руководства, технической команды или поставщика.

## 4. Основной пользовательский путь

### Шаг 1. Выбор объекта

Пользователь выбирает отрасль и тип объекта. Для склада, аэропорта и медицинского учреждения доступны демонстрационные наборы. Система показывает, какие части модели реализованы для выбранного типа объекта полностью, частично или только как прототип.

### Шаг 2. Формирование параметров проекта

Пользователь вводит параметры вручную либо загружает Excel/CSV по шаблону. Для каждого поля показываются единица измерения, пример, допустимый диапазон, обязательность и источник значения по умолчанию.

### Шаг 3. Проверка входных данных

Система проверяет структуру файла, типы, единицы, обязательные поля, допустимые диапазоны и логические связи. Ошибка должна объяснять, что произошло и как исправить значение. Уже сохраненный проект не должен теряться из-за неудачного импорта.

### Шаг 4. Подбор решений

Сначала применяются жесткие ограничения. После этого совместимые и условно совместимые решения ранжируются по прозрачным критериям. Для каждого результата показываются причины включения, ограничения, недостающие сведения и источники характеристик.

### Шаг 5. Сравнение вариантов

Пользователь выбирает минимум два сценария роботизации и сравнивает их с текущим процессом без роботизации. Решение, добавленное вручную вопреки автоматическому отсеву, остается доступным, но помечается предупреждением.

### Шаг 6. Экономика и what-if

Система рассчитывает количество оборудования, CAPEX, OPEX, TCO, годовой эффект, срок окупаемости и ROI. Пользователь видит формулы, исходные значения и допущения, может изменить разрешенные параметры и сравнить результаты в одной таблице.

### Шаг 7. Имитация

Пользователь запускает 2D-модель выбранного сценария, меняет скорость воспроизведения, останавливает и перезапускает расчет. Модель показывает движение по маршрутам и расчетные KPI: выпуск, загрузку, очереди, простои, зарядку и узкие места.

### Шаг 8. Сохранение и экспорт

Пользователь сохраняет проект и экспортирует отчет и расчетную таблицу. Повторное открытие должно воспроизводить результат по сохраненным версиям каталога, нормативов и расчетной модели.

## 5. Функциональные требования

Приоритеты:

- P0 — необходим для целостного конкурсного сценария;
- P1 — важен для финальной версии, но может быть упрощен;
- P2 — преимущество или развитие после базового MVP.

### 5.4. Подбор и объяснимость

| ID | Приоритет | Требование | Минимальная проверка |
| --- | --- | --- | --- |
| REC-01 | P0 | Жесткое ограничение исключает несовместимое решение | Недостаточная грузоподъемность дает статус «не применимо» независимо от балла |
| REC-02 | P0 | Недостаток данных не приравнивается к совместимости | Решение получает статус «требует проверки» и список недостающих полей |
| REC-03 | P0 | Ранжирование объяснимо | UI показывает критерии, веса и вклад факторов |
| REC-04 | P0 | Результат содержит причины соответствия и ограничения | Объяснение строится из реально сработавших правил |
| REC-05 | P1 | Пользователь может вручную добавить исключенный вариант | Сравнение сохраняет предупреждение и причину исключения |
| REC-06 | P1 | Версия правил сохраняется вместе с расчетом | Повторный запуск старого проекта использует сохраненную версию либо явно предлагает миграцию |

Канонический enum результата:

- `applicable` — все жесткие ограничения пройдены на подтвержденных данных;
- `applicable_with_assumptions` — ограничения пройдены с явно принятыми и сохраненными допущениями;
- `needs_review` — данных недостаточно, чтобы подтвердить или опровергнуть применимость;
- `not_applicable` — нарушено хотя бы одно жесткое ограничение.

`needs_review` не является разновидностью применимости. После заполнения недостающих данных или принятия явного допущения результат пересчитывается и переходит в `applicable`, `applicable_with_assumptions` либо `not_applicable`. Любое изменение входов или версии правил запускает повторную оценку статуса.

## 6. Нефункциональные требования

### 6.1. Производительность

- Каталог, формы и проекты должны работать без заметных задержек при пилотной нагрузке до 50 одновременных пользователей.
- Типовой экономический расчет должен завершаться не более чем за 10 секунд.
- Имитация может выполняться до 60 секунд с видимым статусом.
- Импорт должен быть атомарным: ошибка не оставляет частично обновленный проект или каталог.

### 6.2. Безопасность

Все требования этого подраздела имеют приоритет P0 и являются обязательным gate для развертывания demo/staging.

- Пароли хранятся только в виде стойкого хеша.
- Каждый запрос к проектным ресурсам выполняется от имени идентифицированного субъекта: зарегистрированного пользователя либо изолированной гостевой сессии.
- Авторизация и проверка владельца проекта выполняются на стороне API для чтения, изменения, расчета, экспорта и удаления; знание `project_id` не дает доступа к проекту.
- Проекты разных пользователей и гостевых сессий изолированы. Проверка изоляции обязательна до развертывания demo/staging и не может быть заменена ограничением только в UI.
- Регистрацию и расширенную ролевую модель можно отложить, но нельзя отключать серверную проверку доступа.
- В сетевом развертывании используется HTTPS.
- Загруженные файлы ограничиваются по типу и размеру, сохраняются вне публичной директории и удаляются вместе с проектом.
- Демонстрационные данные не содержат персональных или ограниченных сведений.
- Секреты не попадают в репозиторий, Docker-образы и клиентскую сборку.

### 6.3. Воспроизводимость и аудит

- Компоненты запускаются через Docker Compose или эквивалентную конфигурацию.
- Проект хранит версии каталога, схемы объекта, правил подбора, нормативов и расчетной модели.
- Расчет формирует структурированный журнал примененных правил и допущений.
- Документация позволяет стороннему специалисту запустить продукт и воспроизвести демонстрационный расчет.

### 6.4. Интерфейс

- Основной язык — русский.
- Ключевой сценарий выполняется без инструкции.
- Минимальное поддерживаемое разрешение — 1366 x 768.
- Единицы, подсказки, диапазоны и исправления ошибок показываются рядом с полем.
- Доступность с клавиатуры, контраст и понятные статусы следует включить в критерии готовности, хотя ТЗ не задает формальный стандарт доступности.

### 6.5. Расширяемость

Добавление нового типа объекта, параметра, типа решения или расчетного модуля не должно требовать изменения существующих доменных таблиц и логики интерфейса для каждого нового поля. Это означает использование метаданных схем, версий и подключаемых правил, но не требует универсального low-code конструктора в MVP.

## 7. Предлагаемая граница MVP

### Обязательно полностью

- склад как основной объект;
- гостевой демо-путь с изолированной серверной сессией;
- ручной ввод и импорт параметров;
- каталог из локального снапшота;
- технический отсев и объяснимое ранжирование;
- три сценария;
- прозрачная экономика и чувствительность;
- связанная с расчетом 2D-имитация;
- сохранение и воспроизведение проекта;
- итоговый экран и как минимум один открываемый экспорт;
- Docker Compose и инструкция запуска.

### Обязательно показать, допустимо упростить

- отдельные схемы параметров аэропорта и медучреждения;
- доступные типы решений для всех трех объектов;
- администраторский импорт каталога;
- регистрация пользователей и расширенная ролевая модель; базовая авторизация API и изоляция проектов остаются обязательными;
- PDF и XLSX одновременно: допустимо сначала надежно реализовать один формат и явно обозначить статус второго.

### После основного MVP

- автоматическое обновление из внешних источников;
- полноценная экономика аэропорта и медучреждения;
- сложная пространственная модель объекта;
- интеграции с промышленными системами;
- кредит, лизинг и расширенные финансовые показатели;
- ML-ранжирование;
- роль вендора;
- государственные реестры и меры поддержки.

## 8. Демонстрационный сценарий

Для живой демонстрации рекомендуется один заранее проверенный проект склада:

1. Загрузить базовые значения листа «Склад».
2. Изменить объем отбора, стоимость персонала и бюджет.
3. Показать отклонение вне диапазона и исправление.
4. Получить список решений, включая хотя бы одно исключенное и одно требующее проверки.
5. Сравнить текущий процесс, покупку AMR и RaaS.
6. Открыть формулы и происхождение цены.
7. Изменить три допущения и показать чувствительность.
8. Запустить имитацию, показать загрузку и узкое место.
9. Сохранить проект, открыть повторно и экспортировать отчет.

Отдельным коротким проходом нужно показать наличие форм для аэропорта и медучреждения.

## 9. Критерии готовности продукта к финальной сдаче

- Чистое окружение запускается по документированной команде.
- Демо не зависит от доступности внешних сайтов.
- Контрольный проект воспроизводит заранее проверенные числовые результаты.
- Все заявленные функции помечены как готовые, частичные или прототипные.
- Нет необъяснимых коэффициентов и скрытых ручных исправлений.
- Исключенные решения не попадают в рекомендации из-за высокого балла по другим критериям.
- Экспорт совпадает с сохраненным проектом.
- Основные API, структура данных и алгоритмы задокументированы.
