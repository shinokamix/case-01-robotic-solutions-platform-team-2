# План перехода к спецификациям и разработке

## 1. Текущий этап

Выполнена верхнеуровневая проработка:

- разобраны конкурсное ТЗ и дополнительные пояснения;
- проверен смысл Q&A-файла;
- изучены демонстрационные параметры объектов;
- выполнен структурный профиль каталога;
- определены границы MVP;
- предложены архитектура, структура монорепозитория и CI/CD-направление;
- сформирован список решений, которые нужно согласовать.

Код продукта, OpenSpec-изменения и инфраструктура на этом этапе не создаются.

## 2. Следующий шаг

Команда подтверждает или корректирует [решения и открытые вопросы](04-open-questions.md) и назначает владельцев для [реестра блокеров](06-development-blockers.md). Каркас монорепозитория, Go-backend, frontend, PostgreSQL и PR CI можно начинать без закрытия всех продуктовых вопросов. До реализации соответствующих доменов достаточно согласовать:

1. основной объект и процесс;
2. границу поддержки трех типов объектов;
3. правила использования цены из каталога `v4`;
4. обязательные ТТХ;
5. базовую экономическую модель покупки и RaaS;
6. уровень имитации;
7. площадку деплоя.

После этого можно создавать OpenSpec-изменения. Репозиторий уже настроен на цикл `specs -> tasks`.

## 3. Предлагаемая последовательность OpenSpec-изменений

### Волна 1. Основа и данные

1. `establish-platform-foundation`
   - структура монорепозитория;
   - frontend на React и TypeScript с Vite+ без SSR;
   - Go-backend;
   - минимальная модель principal и изолированной гостевой сессии;
   - обязательная серверная авторизация проектных API;
   - локальный Docker Compose;
   - общие проверки.

2. `normalize-catalog-and-object-data`
   - версии наборов данных;
   - схемы импорта;
   - каталог, применимости, цены и provenance;
   - контроль качества подготовленных данных.

3. `manage-project-input`
   - проекты;
   - владение проектом и проверка межпроектной изоляции;
   - схемы объектов;
   - ручной ввод;
   - импорт и валидация;
   - сохранение снимка входов.

### Волна 2. Основная ценность

4. `recommend-robotic-solutions`
   - жесткие ограничения;
   - статусы неизвестности;
   - ранжирование;
   - объяснения;
   - ручное добавление варианта.

5. `compare-economic-scenarios`
   - состав оборудования;
   - базовый сценарий, покупка и RaaS;
   - CAPEX/OPEX/ROI/TCO;
   - допущения, корректировки и чувствительность.

6. `simulate-warehouse-operations`
   - схема объекта;
   - дискретно-событийная модель;
   - KPI и трасса;
   - управление воспроизведением.

### Волна 3. Завершение пользовательского пути

7. `export-project-assessment`
   - итоговый экран;
   - PDF;
   - табличный экспорт;
   - снимок визуализации.

8. `extend-access-and-manage-catalog`
   - регистрация и расширенная ролевая модель поверх обязательной базовой авторизации;
   - административный импорт;
   - публикация версий;
   - аудит изменений.

9. `deploy-demo-platform`
   - контейнеры;
   - registry;
   - GitHub Actions;
   - demo/staging;
   - smoke test и откат.

Названия являются предварительными. Одно OpenSpec-изменение может содержать несколько спецификаций возможностей, но не должно смешивать несвязанные пользовательские результаты ради уменьшения числа изменений.

## 4. Как будут формироваться спецификации

Для каждой возможности будут определены:

- назначение и границы;
- основная user story;
- обязательное наблюдаемое поведение;
- положительные, ошибочные и граничные сценарии;
- общие контракты данных;
- формулы, единицы и округление, если применимо;
- производительность и безопасность;
- проверяемый план задач с владельцами `frontend`, `backend`, `ml`, `infra`.

Сначала создаются и проверяются `specs`, затем `tasks`. Реализация начинается только отдельным этапом после согласования изменения.

## 5. Параллельная работа команды

После появления контрактов задачи можно вести параллельно:

- frontend собирает путь пользователя на сгенерированном API-клиенте и mock-данных;
- backend на Go реализует модель проекта, каталог и расчетные контракты;
- data/ML нормализует источники, инвентаризирует дополнительные данные, проектирует разметку, обогащает ТТХ и готовит правила качества;
- infra создает Docker и CI без привязки к незавершенной бизнес-логике.

Параллельность безопасна только после фиксации общих контрактов: идентификаторов, единиц, статусов применимости, версий модели и формата ошибок.

## 6. Контрольные точки

### Контрольная точка A. Данные готовы

- импортируемые файлы имеют версию;
- каталог нормализован;
- выбранные решения содержат обязательные ТТХ;
- источники и допущения привязаны к значениям;
- контрольные примеры проходят data-quality тесты.

### Контрольная точка B. Вертикальный путь без имитации

- проект склада создается и валидируется;
- проект недоступен другому пользователю или другой гостевой сессии;
- подбор объясним;
- три сценария рассчитываются;
- результат сохраняется и воспроизводится.

### Контрольная точка C. Имитация подтверждает расчет

- модель использует тот же снимок сценария;
- throughput и загрузка отображаются;
- узкое место видно в KPI и на схеме;
- результат воспроизводим.

### Контрольная точка D. Финальная демонстрация

- чистый запуск по инструкции;
- основной путь проходит без ручного исправления базы;
- три типа объектов показаны в согласованной глубине;
- экспорт совпадает с экраном;
- развернутая версия проходит smoke test.

## 7. Минимальная стратегия тестирования

### Frontend

- unit-тесты преобразований и состояния формы;
- component-тесты ключевых состояний;
- end-to-end тест полного демо-пути;
- проверка разрешения 1366 x 768.

### Backend

- `gofmt` и статический анализ Go-кода;
- unit-тесты правил и формул;
- граничные тесты экономики для нулевого CAPEX и неположительного годового эффекта;
- property-based тесты числовых границ, если оправдано;
- integration-тесты API и PostgreSQL;
- негативные тесты доступа к чужому проекту для каждого проектного endpoint;
- тесты изоляции зарегистрированных пользователей и гостевых сессий;
- тест атомарности импорта.

### Data и ML

- схема, типы, обязательность, единицы;
- уникальность продуктовых ключей;
- ссылочная целостность применимостей;
- валидность цены и даты;
- полнота критических ТТХ;
- воспроизводимость подготовки данных;
- проверка отсутствия утечки между train/validation/test;
- baseline и ML-метрики только после фиксации задачи и получения размеченной выборки.

### Infrastructure

- сборка каждого контейнера;
- запуск Compose;
- миграции на пустой базе;
- health/readiness;
- smoke test после деплоя;
- отсутствие секретов в образах и логах.

## 8. Что пока сознательно не делаем

- не создаем формальные OpenSpec-спецификации до согласования решений;
- не выбираем окончательные версии библиотек;
- не создаем папки приложений и шаблонный код;
- не интегрируем ML в основной путь до проверки датасета, baseline и критериев качества;
- не добавляем внешние источники без проверки;
- не проектируем CD без выбранной площадки;
- не утверждаем точные финансовые результаты до появления контрольного расчета.
