# Краткое описание платформы подбора роботизированных решений

## Статус документа

Документ фиксирует продукт, границы MVP, работу с данными и архитектуру. На основе документа команда готовит OpenSpec-спецификации.

Дата анализа: 15 сентября 2026 года.

## Что требуется построить

Нужно создать веб-платформу для предварительной оценки роботизации. Пользователь описывает склад, аэропорт или медицинское учреждение. Платформа подбирает решения, объясняет выбор, сравнивает покупку с RaaS и рассчитывает экономику. Пользователь может проверить производительность и выгрузить отчет.

Платформа формирует проверяемую гипотезу. Результат отвечает на пять вопросов: какое решение применимо, почему, сколько оборудования нужно, какой экономический эффект ожидается и какие данные нужно подтвердить перед пилотом.

Платформа не заменяет обследование объекта, детальное проектирование или полноценное технико-экономическое обоснование.

## Граница MVP

Основной сценарий MVP охватывает склад:

1. Создание проекта и загрузка демонстрационных параметров склада.
2. Проверка входных данных.
3. Отсев технически несовместимых решений.
4. Объяснимое ранжирование оставшихся вариантов.
5. Сравнение трех сценариев: без роботизации, покупка, RaaS.
6. Расчет количества роботов, CAPEX, OPEX, TCO, годового эффекта, срока окупаемости и ROI.
7. What-if анализ минимум по трем параметрам.
8. 2D-имитация, связанная с расчетной производительностью.
9. Сохранение проекта и экспорт отчета.

Для аэропорта и медицинского учреждения MVP включает выбор типа объекта, отдельные формы параметров и подбор типов решений. Полная экономика и имитация для этих объектов не входят в MVP.

## Ключевые продуктовые решения

- Подбор должен состоять из жестких правил применимости и прозрачной балльной оценки. Нельзя скрывать несовместимость за высоким суммарным баллом.
- Экономическая модель должна быть детерминированной, версионируемой и воспроизводимой. Любое ручное изменение исходного значения фиксируется вместе с причиной.
- Имитация должна проверять пропускную способность, загрузку, очереди, простои и узкие места. Декоративное движение иконок не удовлетворяет ТЗ.
- Каталог и нормативы должны работать локально на заранее загруженной версии. Внешние сайты не могут быть обязательной зависимостью демонстрации.
- Для каждого результата нужно показывать происхождение данных, дату актуальности, степень подтвержденности и недостающие характеристики.

## Роль ML

Предоставленные файлы не содержат обучающих меток вида «параметры объекта -> успешное решение» и сами по себе не позволяют обоснованно обучить рекомендательную модель. При этом команда предполагает, что сможет получить дополнительные данные, поэтому ML нужно вести отдельным параллельным треком уже с начала проекта: определить задачу, контракт датасета, источники, правила разметки и критерии качества.

Основа подбора в MVP остается правиловой и расчетной. Это позволяет начать разработку до получения расширенного датасета и не превращает доступность ML-модели в блокер всего продукта.

ML можно добавить как вспомогательную функцию:

- семантический поиск по описаниям каталога;
- извлечение характеристик из документов;
- нормализация категорий;
- поиск похожих кейсов;
- обучение ранжирования или классификации применимости после получения и проверки дополнительной выборки;
- последующее улучшение модели на накопленной обратной связи экспертов и результатах пилотов.

ML не должен определять критические ограничения, экономические формулы или итоговую рекомендацию без объяснения.

## Архитектура

- Frontend: одностраничное приложение на React и TypeScript. Для разработки, проверок, тестов и сборки используется Vite+. SSR не используется.
- Backend: Go как модульный монолит с четкими доменными границами.
- Хранилище: PostgreSQL.
- Фоновые вычисления: отдельный worker только для имитации и тяжелых импортов; в первой версии допустим синхронный запуск с контролем времени.
- ML: отдельная Python-зона монорепозитория для подготовки данных, экспериментов, обучения и опционального inference-сервиса; основной Go-backend сохраняет работоспособность без нее.
- Контракты: OpenAPI и генерируемый TypeScript-клиент.
- Локальный запуск: Docker Compose.
- CI/CD: GitHub Actions для проверок, сборки контейнеров и контролируемого деплоя.

Подробная схема приведена в [концепции решения](03-solution-concept.md).

## Известные факты и риски исходных материалов

1. Имя `catalog_export_v5` в дополнении к ТЗ содержит опечатку. Рабочий датасет называется `catalog_export_v4`.
2. Каталог содержит 223 строки, но только 187 уникальных `id`; один продукт может повторяться для разных отраслей и сценариев.
3. В каталоге нет большей части обязательных ТТХ для технического подбора.
4. Для 51,6% строк каталога отсутствует описание, для 30,0% — верхнеуровневый тип, для 35,9% — подтип.
5. У каталога нет структурированных ссылок на источник, даты актуализации, валюты, даты цены и признака подтвержденности.
6. Демонстрационная книга описывает нормативы и параметры одного типового объекта каждого вида, но не содержит исторических наблюдений или результатов внедрения для обучения ML.
7. Файл про Q&A содержит регламент сессии, но не содержит ответов организатора. Возможные уточнения после сессии в репозитории пока отсутствуют.

Подробнее: [оценка исходных данных](02-data-assessment.md).

## Решения перед спецификациями

Версия каталога и стек frontend уже зафиксированы. Перед созданием OpenSpec команда должна утвердить остальные рабочие решения:

| Вопрос | Рабочее решение |
| --- | --- |
| Какой объект реализуем полностью | Склад |
| Что является ядром подбора | Жесткие ограничения и объяснимая балльная модель |
| Нужен ли ML в критическом пути MVP | Нет, но получение и разметка дополнительных данных начинаются параллельно |
| Как трактовать повторяющиеся `id` | Продукт и его применимость хранить раздельно |
| Как запускать демонстрацию | Полностью из локально загруженных данных |
| Как строить backend | Модульный монолит на Go, а не набор микросервисов |
| Как считать RaaS | Отдельный сценарий с явно настраиваемой структурой платежей |
| Как организовать доступ в первом проходе | Авторизация API и изоляция проектов обязательны; регистрацию и расширенные роли можно упростить, гостевой путь работает через изолированную сессию |

Полный список: [решения и открытые вопросы](04-open-questions.md). Вопросы, способные остановить конкретные части разработки, вынесены в отдельный [реестр блокеров](06-development-blockers.md).
